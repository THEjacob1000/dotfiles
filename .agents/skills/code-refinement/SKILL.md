# Code refinement

Refine correctness and maintenance cost together. This skill owns the scope, stages, and verification. Load the target repository's instructions, `code-golf`, and the relevant language guidelines before deciding what to change; use code-golf's candidate patterns and proof rules inside the current lane, not as a second sweep or a recursive restart of refinement. Code-golf is a criterion for **every** fixer, not an optional last pass: for each candidate, identify the obligation, ask whether a responsibility, state, branch, layer, dependency, or ownership handoff can disappear, and accept only a supported, readable reduction. A shorter implementation that hides an invariant, compresses names, adds avoidable work, or makes the flow harder to understand loses to clear code. Equally, don't preserve redundant complexity merely because it passes checks. Correctness, security, public behavior, compatibility, resource constraints, and repository architecture are hard boundaries. Strict repository policy wins over either skill's general advice. Don't run one whole-repo guidelines rewrite followed by a second whole-repo golf rewrite.

## Scope and route

Interpret the request before editing. An **audit** inventories and ranks candidates, contracts, proof needs, and uncertainty without mutation. **Focused** work changes the named component or behavior and its real callers/boundaries; it doesn't opportunistically sweep unrelated packages. A **sweep** inventories every owned component in the stated scope and works through it in dependency stages. A few cosmetic fixes do not complete a sweep. Mark every area accepted, rejected, blocked, or uninspected. Follow [component and language routing](references/routing.md) to classify manifests, active source, workspace membership, generated code, CI, toolchain, and verification commands. Never pick one language by extension majority. Load `rust-guidelines` for Rust, `go-guidelines` for Go, and the applicable repository conventions plus `coding-standards` for TypeScript/JavaScript. Load framework guidance only when the affected component actually uses that framework. Other languages retain their own repository-native rules and gates; absence of a dedicated skill isn't permission to omit them. Load code-golf's relevant language, workflow, and proof sections on demand, not its entire library at once.

Select each component's repository-native verification route before taking its baseline. Rust's existing helpers are an optional stricter route when that gate is selected, not a mandatory gate for every Rust refinement. Keep the selected route and baseline through the work: don't skip or switch gates mid-run to evade a failure, and don't introduce a new ledger parser or cross-language runner.

Establish a before-state from actual commands and their results: working tree and user-owned changes, component/consumer inventory, package and dependency boundaries, supported feature/build/version variants, existing failures, diagnostics, test totals or an explicit unavailable count, and measured constraints where material. Distinguish an invocation error from a red baseline and a red baseline from a passing gate. An audit's proposal is not a verified edit; recheck relevant facts before execution. Discover contracts in callers, external entry points, tests, schemas, deployments, and build variants. Static search or an apparent absence of callers never proves a path dead.

## Choose and change

Rank opportunities by maintenance burden, contract risk, and evidence, not lines removed. Prefer moving an invariant into the type system over checking it at runtime: a state the compiler rejects needs no test, so the runtime check and the tests that only exercised that state go with it, and the test count should fall. Review relevant language rules beyond scanner hits: a scanner is a lead, not a substitute for judgment. For each candidate, name the current responsibility, proposed cut, supported behavior and failure cases, readability effect, and witness that could falsify equivalence. Reject a shorter but denser rewrite and keep boundaries that enforce invariants, security, or genuine replaceability. Every lane reports its net production and test line change; net growth is acceptable only where it names the invariant the compiler now enforces or the obligation it serves. If one candidate needs authorization, a missing tool, or an unresolved proof, record the blocker **and continue other safe in-scope candidates**. Don't suppress diagnostics, weaken tests, install tooling automatically, or change public behavior under a cleanup label.

For a sweep, order changes by dependency: shared types, APIs, and schemas before libraries, adapters, and consumers; keep cycles or shared compilation units together. Give disjoint lanes settled interfaces and file ownership, with one integration owner for shared manifests, configuration, generated artifacts, APIs, and caller migrations. Concurrent fixers inspect and edit only their owned paths, use both their language guidance and code-golf for each coherent contract, and run no build, test, lint, formatter, or other verification command, even a scoped one that could observe siblings' partial changes. The sole verifier checks the integrated stage after files are stable. A small single-agent focused edit needs no lane or verifier ceremony. Complete each accepted cutover: update every caller, affected tests, documentation, and wiring; remove superseded exports and wrappers instead of retaining compatibility shims without an actual supported contract.

Treat tests as obligations rather than a number to game. Follow code-golf's proof-and-tests policy per assertion: keep meaningful boundary and regression checks, migrate them when the entry point changes, and retire a test whose case the compiler now rejects, or whose obligation is otherwise gone, with the surviving witness named. Never delete tests to hide failures, ignore tests, weaken assertions, pad counts, or treat compiler success as proof for untrusted runtime input: parsing, deserialization, FFI and authorization boundaries keep their runtime tests. Review baseline and current test identities and obligations, not just aggregate totals. The strict Rust helper tracks test identities: it lists retired tests for that review and goes red when a previously failing test disappears or ignored tests increase. Don't switch gates to evade this policy. On a repository-native route, review each removal and surviving witness the same way and disclose count changes. For the optional helpers' exact semantics, read [Rust tooling](references/rust-tools.md).

## Verify and close

Integrate a coherent stage before verification. One verifier, separate from fixers, runs affected native checks and actual entry-point scenarios after the shared surface is stable, including supported error cases and relevant version, feature, target, or build variants. The same verifier runs the final repository gate over the requested scope after all stages, comparing actual baseline and final evidence; never claim unexercised variants or unavailable totals passed. Fix root causes in bounded fix/verify rounds, at most three for a sweep, rather than looping indefinitely or resetting the baseline to conceal regressions. If checks remain red, report the exact failure and affected scope; don't call it complete. Obtain an independent code review, resolve findings, and revisit affected checks when fixes change behavior. Report actual reductions and retained seams with reasons, observed verification, changed test obligations and counts, plus rejected, blocked, and uninspected areas. A partial sweep stays partial even if the edited lanes pass. Don't create permanent reports or extra infrastructure for a focused edit unless repository policy needs them.
