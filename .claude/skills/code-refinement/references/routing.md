# Route by owned component, not dominant language

Start from the requested paths and the repository's instructions. Inspect root and nested manifests, workspace membership, active source, imports/build inclusion, package scripts, CI workflows and referenced scripts, generators, toolchain pins, and supported configuration variants. The nearest manifest often establishes ownership, but workspace declarations and CI may connect several packages. Classify maintained source, tests, examples, build scripts, and config separately from third-party or generated output. Exclude a tree only with positive evidence (generator/manifest declaration, vendored dependency metadata, repository policy, or CI treatment), not just a name such as `vendor` or `generated`. If generated output is owned or checked in as the source of truth, follow its repository policy; otherwise change the generator and regenerate through the declared process. Shared root policy belongs to one integration owner.

| Evidence in a component | Load for affected work | Watch |
| --- | --- | --- |
| `.rs` source with a `Cargo.toml` package/workspace | `rust-guidelines` and `code-golf`'s Rust section | `build.rs`, tests/examples, `cfg`, features, target, MSRV/toolchain, and workspace dependencies. Rust helpers in this skill are Rust-specific. |
| `.go` source with `go.mod` or `go.work` members | `go-guidelines` and code-golf's Go section | Nearest module, workspace membership, Go version, build tags, platforms, race-sensitive paths. |
| `.ts`/`.tsx` source actively built or run in a package | Repository conventions, relevant `coding-standards`, and code-golf's TypeScript/JavaScript section | Runtime, `tsconfig` inclusion/references, target/module mode, bundler, typecheck and cross-package consumers. A tooling-only TypeScript file is a maintained tooling component, not proof that the app runtime is TS. |
| `.js`/`.jsx`/`.mjs`/`.cjs` source actively built or run | Repository conventions, relevant `coding-standards`, and code-golf's TypeScript/JavaScript section | Package `type`, extension semantics, runtime, scripts, and imports. JS-only packages stay JS-only; do not prescribe TS migration. |
| Other maintained languages | Their repository-native conventions and existing verification | No invented guideline and no silent omission; identify ownership and contract explicitly. |

A `package.json` used only for formatter, bundler, or release tooling does not turn a Rust or Go application into a JavaScript runtime. If its scripts or config code are in scope, route that tooling as a component and check only its actual contract. A root `tsconfig` with no runtime TS source similarly does not relabel neighboring JS packages. Mixed-source packages can require several guides: partition work by real ownership and contracts, not an extension vote. Nested modules take their own manifest's version and gate; shared config and cross-language interfaces require coordinated review. `frontend-patterns`, `backend-patterns`, `api-design`, and framework-specific guidance are optional only when the affected code actually uses the relevant framework or API surface. Generic recipes do not outrank correctness, readable code, project architecture, or existing conventions.

Resolve **package manager**, **runtime/toolchain**, and **test runner** separately. For example, `packageManager` and a lockfile suggest how dependencies are managed, but do not establish whether scripts execute under Node, Bun, a browser, or another runtime; a test dependency does not establish the CI command. Inspect package scripts and the CI commands that invoke them, including delegated scripts, flags, workspace selectors, environment, and lockfile policy. Prefer documented task/CI invocations over invented global commands. For Rust, preserve the project's Cargo toolchain, features, targets and lock policy; for Go, preserve module/workspace, version and build-tag matrix. For TS/JS, use declared package scripts and supported module/bundler targets. If CI supports several version, feature, target, platform, SSR/browser or build variants, map the changed obligation to each affected row. State which rows were exercised and which remain unknown. Don't automatically install tools or dependencies, silently substitute a runner, or call a default build an entire matrix. If an opaque script cannot be resolved, identify the missing command or configuration instead of fabricating one.

Choose and record the verification route for each component before baseline. Repository-native CI/tasks are the default. The Rust helper gate documented in [Rust tooling](rust-tools.md) is an optional stricter route when selected; it is not a universal Rust requirement or a model for a new generic runner. Its comparison rejects fewer passing tests or suites and more ignored tests, not changes in test identity. The strict route also requires review that no test obligation was removed or weakened, even when aggregate counts pass. A native route can retire an individually reviewed obsolete obligation only where repository policy permits it. Never switch or omit the chosen gate midway to turn a failing result green; report blocked retirement or incomplete verification instead.

Decision examples, without tool output:

- A Cargo-only crate with a tooling-only `package.json`: Rust application gets `rust-guidelines` and Rust code-golf; JS tooling gets JS guidance only if its maintained scripts/config are part of the request. Use the crate's real Rust CI gate, not package scripts as an app test.
- A JS-only package beside a TS package: route the first to JS behavior and its own declared test script, the second to TS behavior and its declared checks. Do not force a TS migration or borrow sibling `tsconfig` settings.
- A `go.work` root with nested Go modules, a Rust workspace and one TS build-tool package: cover the affected Go modules, Rust crates and TS tooling independently, then include their shared CI variants. No majority language is selected, and an unrelated lane is not marked verified by another lane's gate.
