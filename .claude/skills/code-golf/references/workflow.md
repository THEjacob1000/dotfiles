# Reduction workflow

The unit of work is a proved reduction of an obligation, not a shorter diff. Choose audit, focused execution, or whole-repository sweep from the request. An audit never edits; execution does not treat its audit as fresh proof. Apply the target repository's instructions and architecture gates before this workflow. Work without ripwire or agents when unavailable.

## 1. Establish the boundary

Read the requested scope, repository instructions, build topology, language/toolchain versions, and any design constraints on public interfaces, trust boundaries, compatibility, deployment, and performance. Check the working tree before edits. Existing changes belong to the user: record them, work around them, and don't reset or claim them. For a focused edit, identify the target and its immediate consumers and boundaries. For a sweep, enumerate every workspace/package/module in the stated scope, including binaries, libraries, build variants, generators, tests, and integration surfaces. A directory count alone is not an inventory. Exclusions require a stated reason; work not examined is *uninspected*, not clean.

Capture a baseline appropriate to the project: relevant builds and tests, existing failures, source and test inventory, dependency graph, diagnostics, public surface, and any measured performance or bundle-size constraint. Save actual command, environment, configuration, and result where comparison matters; unavailable counts stay unavailable, not zero. Don't use a pre-existing red gate as an excuse to drop a failing test or silently narrow the task. An invocation failure is not a passing baseline. In a large sweep, a fast scoped baseline can precede work, but the final gate must cover the full stated scope; note any initial check that could not run.

## 2. Inventory and rank candidates

Search by responsibility and behavior, not just by suspicious syntax. Inspect owners of similar policy, callers, interfaces and implementors, data flow, schemas, config, adapters, test fixtures, package manifests, and actual entry points. Use native repo search and LSP find-references/implementations where available. Include public exports, indirect calls, generated registration, reflection, plugins, FFI, dynamic imports, serialized forms, build tags/conditional compilation, and downstream consumers in the reachability question. Searches and call graphs have blind spots. Ripwire, if installed, can rank or orient candidates and callers; its deadness estimate is a lead, never deletion proof.

Record each candidate's location, responsibility, proposed transformation, expected payoff, contract at risk, evidence needed, dependencies, and disposition. Prefer eliminating duplicated policy, unused state or work, needless indirection, redundant data representations, and dependencies whose responsibility can disappear. The [reduction catalog](reductions.md) supplies counterexamples and proof prompts. Rank by maintenance burden and confidence, not raw lines: an easy one-line cleanup should not displace a central duplicated state machine if the latter is in scope. A candidate is **accepted** only after its contract and check are identified; **rejected** when preserving it is the right decision; **blocked** when a real prerequisite prevents resolution; **uninspected** when the stated scope has not been examined. Revisit dispositions when integration reveals new evidence.

For an audit, stop here after evaluating candidates and their likely blast radius. Give a ranked set of concrete decisions, proof obligations, and the accepted/rejected/blocked/uninspected inventory. Do not claim a prospective reduction has already been proved, and do not mutate code to make the audit look productive.

## 3. Plan execution by dependencies

Draw edges for producers before consumers: shared types, exported APIs, schemas and generated code, core libraries, adapters, application wiring, then dependent tests and docs. Put a cycle or shared compilation unit in one lane. An independent lane owns disjoint files and a settled interface contract. Assign one integration owner to shared API definitions, manifests, lockfiles, generated artifacts, and cross-package caller migration. Don't let concurrent workers edit the same shared surface; serialize that boundary, not unrelated work. If a proposed change requires a shared edit, hand the requirement to the owner rather than leaving an incompatible caller. No lane can declare a cutover complete while old callers, exports, docs, or tests still depend on the removed path.

Work in stages from foundations toward consumers. Concurrent lanes in one stage can edit independently, but they should not each run a project-wide suite over siblings' half-finished files. The integrating owner reviews interface changes and migrates every caller before the next dependent stage. Small focused changes need no lane machinery. A sweep does not need a custom orchestrator: a simple inventory and agreed ownership suffice.

## 4. Reduce and prove locally

For each accepted candidate, establish its observable obligation first. Compare the old and proposed behavior for normal, boundary, and error paths; include compatibility, cancellation, resource lifetime, security, performance, and concurrency where applicable. Readability is a hard acceptance condition: the change must leave fewer things for a reader to understand without making the remaining flow harder to follow. Reject a shorter but denser proposal, including clever chains, compressed names, macro/type tricks, hidden effects, or abstraction indirection; clear longer code wins. Delete the responsibility itself when possible; a helper extraction that merely relocates it is not a reduction. Keep architectural seams that enforce a genuine invariant, limit the trusted computing base, or support specified swappability. Don't use a compile-time check as a substitute for a runtime boundary or add a duplicate convention next to the existing one.

Edit one coherent contract at a time and update its callers, tests, documentation, and generated/build configuration as needed. Verify the changed path with the smallest meaningful runtime or compile/build scenario, including failure behavior that could plausibly regress. For proof limits and per-test keep/migrate/retire decisions, use [proof and tests](proof-and-tests.md). A test can retire only if project policy permits it and the ledger says which obligation moved to which enforceable mechanism or became unsupported. Source deletion, type checking, test passage, and static reachability are different kinds of evidence. Benchmark with comparable conditions before claiming speed or allocation improvements.

At a stage boundary, integrate the lanes, inspect the combined diff and public contracts, then run the affected build variants and focused tests after shared files are stable. Diagnose failures at source; never suppress a diagnostic or weaken a test to make a reduction look green. If the contract cannot be preserved within the requested scope, reject the proposal or report a blocker rather than ship a partial cutover. Update the inventory, including newly discovered candidates and affected packages.

## 5. Close the sweep

When all lanes are integrated, exercise the actual affected entry points and run the repository's final verification gate over the stated scope and relevant configurations. Run it again after any fixes needed to clear regressions, not once per independent lane. Compare against the recorded baseline: diagnostic changes, retained and retired test obligations, dependency removals, modified public APIs, build outputs, and measured costs when claims depend on them. Resolve unexpected regressions, or identify exactly which remain and why. A green check proves only what that check covers; external consumers, runtime-loaded code, and deployments may need distinct evidence. Don't report a numerical improvement from estimates or a count whose baseline was unavailable.

Report concise before/after evidence, actual reductions, retained abstractions and reasons, migrated callers, retired tests with their obligations, and any residual risks. For a sweep, close every inventoried area as accepted, rejected, blocked, or uninspected; give a count and names or paths for blocked and uninspected areas so breadth is auditable. Incomplete scope remains incomplete even if the edited subset passes. For a focused edit, a compact account is enough; don't create a permanent ledger or report file unless the project requires one. Remove temporary experiment artifacts after their evidence has been captured, without deleting user-owned work.
